# An owned skeleton is frozen, derived state has one lifecycle, and world up is guessed once

A `Bvh` holds three kinds of state. **Primary state** is its skeleton and its motion. **The user's settings** are the world-up override, the preference for the world-up disagreement warning and a user L/R mapping. **Derived state** is every value computed from those: the forward-kinematics positions, the rest-pose positions, the scene ground (`floor_height`), the guessed world up, the node and joint indexes, and the L/R mapping detected from names. Through v0.9.0 each derived value had its own convention for when it was filled, cleared and copied, and the skeleton could change under all of them. From v0.10.0 three decisions keep derived state true to the state it was computed from.

## Decision

**1. A skeleton owned by a `Bvh` is frozen, and pybvh's own edits replace it.** Once a node has been passed to `Bvh(...)`, its name, offset, parent, children and channels refuse assignment with an `AttributeError` that names the way to make the change: `bvh.to_node_table()`, edit the table, `bvh.copy(nodes=table)`. That copy is a derived clip like any other (decision 2): it binds the motion to the new joints by position, so the joint count and each joint's Euler order stay, inherits the world up (decision 3), and carries a user L/R mapping to the joints' new names by position. Its offset is a read-only array and its children a tuple. Its channel orders are tuples on every node, owned or not, so none changes in place. A clip has no `nodes` or `root` setter; `root` is `nodes[0]`. `nodes` is a tuple the clip makes from the nodes it is given, so neither an edit through it nor one to the list the caller passed reaches the skeleton. Nodes not yet owned stay mutable, so a skeleton can still be built by hand before it reaches the constructor. When pybvh itself changes a skeleton (`scale`, `mirror`, `retarget`, the rest reorientations, `reorient_world_up`, `change_euler_order`) it builds a new node list through `nodes_from_table` and hands it to one internal replace step, which checks the tree, freezes the new nodes and reports the change. Nothing unfreezes a node, pybvh included.

**2. Derived state has one lifecycle.** A private lifecycle module holds every derived value, the table of what each is computed from, and one method per change event. The inputs are the skeleton, the motion and the world-up override. The events are those three changing, plus a fourth, *the user replaced the motion*, raised by the `root_pos` and `joint_angles` setters and `__setitem__`; pybvh's own motion writes raise *the motion changed*. A value is computed when it is read and found empty, and an event clears every value that depends on it:

| Derived value | Computed from | Cleared by |
| --- | --- | --- |
| node and joint indexes, L/R mapping detected from names | skeleton | skeleton changed |
| rest-pose positions | skeleton | skeleton changed |
| forward-kinematics positions | skeleton, motion | skeleton changed, motion changed, user replaced the motion |
| scene ground | skeleton, motion, world up | skeleton changed, motion changed, user replaced the motion, world-up override changed, L/R mapping setting changed (ADR 0004) |
| guessed world up | skeleton, motion; when it falls back to rest up, the L/R mapping setting (ADR 0004) | user replaced the motion (decision 3); a guess of the clip's own, also L/R mapping setting changed (ADR 0004) |

No edit declares that it preserves a value: every dependent is cleared, and a clip whose input changed pays one recomputation. A clip pybvh derives (a copy, a slice, a concatenation, a resampled clip, a transformed clip, `retarget`, `extract_joints`) and a pickle carry the primary state and the user's settings, and never a derived value. The world up a clip has resolved travels with them as an answer the new clip inherits (decision 3), not as a value it computed. Arrays the lifecycle holds are read-only, so a write into one raises at the line that made it.

**3. World up is guessed once and inherited.** A clip without an override guesses its world up from its first frame, with the rest pose as fallback. Once the guess is made, every clip pybvh derives from that clip reports the same axis, recorded as *inherited*, a third state beside the user's override and the inference. Only the user starts the guess again: by replacing the motion, or, for a guess the clip made itself, by setting the L/R mapping, which rest up reads (ADR 0004); neither clears an override. `reorient_world_up` sets its target axis explicitly, as before, and turns the guess the clip holds by the same rotation it applies to the frames, so clearing that axis gives the one the rotated frames show without guessing again. The guess is therefore the one derived value that survives a change of its inputs: it is cleared by none of pybvh's own edits, skeleton or motion, because none of them changes which way is up except `reorient_world_up`, which says so.

## Why

**The skeleton could change behind the derived state.** A node did not know its `Bvh`, its setters were public and its `offset` getter returned the live array, so no derived value could hear of an edit. Five staleness bugs followed on v0.9.0: (1) setting `world_up` kept the old floor height; (2) editing an offset left the FK positions stale; (3) renaming a node left the name index stale and silently dropped a user L/R pair naming it; (4) assigning `bvh.nodes` left `root` on the old root and the index sized for the old skeleton; (5) `extract_joints` inferred world up, and warned, under an override. pybvh's own in-place offset edits were correct only by the order of their statements relative to a setter that happened to clear the derived values, and `mirror` wrote its offsets after its last such setter. Freezing extends what the code already did for channels; routing every skeleton change through one replace step removes the statement-order hazard instead of documenting it.

**A hint that an edit preserves a value is an invariant held by a comment, and they go wrong.** The architecture review took `harmonize`'s world-up inference after its rest stages for redundant, since rotating the rest pose does not move the world. It is not always: on an ambiguous first frame the inference falls back to rest up, which `reorient_rest_up` changes, so a "rest reorientation preserves the guessed world up" hint would have held a value a fresh inference contradicts. One table, read in one place, has no such hints to keep true.

**Which way is up is a property of the recording, not of the slice.** Cutting a clip, resampling it, rotating it about its up axis or changing its rest pose does not change which way gravity points, but a fresh guess on the derived clip could: a slice whose first frame is a crouch or a fall is ambiguous where its source was not. Inheriting the answer makes every derived clip agree with its source, and makes the guess on the source the only one. It also makes `harmonize`'s stages agree: the old re-inference after the rest stages could flip the axis only because its fallback read rest up while the world had not moved. The user assigning new motion is the one case where the recording itself is replaced, so it is the one case that guesses again.

## How it sits with ADR 0002

ADR 0002 stands: the scene ground is all nodes at the robust 2nd percentile, and the contact detectors never compute or read it. This ADR changes when the scene ground is rebuilt, not what it is: it is cleared on a skeleton change and on a world-up change as well as on a motion change, because it is measured along world up and the v0.9.0 `world_up` setter left it stale (bug 1 above). ADR 0002's rule that contacts never fill or read `floor_height` is now checked as "contacts make zero scene-ground computations".

## Considered options

**For the skeleton.** *A back-reference from node to clip*, so an edit can clear its clip's derived state: rejected because a node list can be shared by two clips, and because it puts the lifecycle in `BvhNode`. *Fingerprinting the skeleton on every read*: rejected for the cost it adds to every read, on the hot paths of the descriptors. *Documenting "don't mutate an owned node"*: rejected because it leaves bugs 2 to 4 in place for anyone who has not read the note. *A context manager that unfreezes and refreezes* for pybvh's own edits: rejected as a back door that any caller can use and that brings the statement-order hazard back.

**For the lifecycle.** *One attribute on `Bvh` per derived value, with the dependency table in a comment*: rejected because the knowledge spreads out again across a 3,700-line module. *`functools.cached_property`*: rejected because it cannot hold the user's settings and clears per attribute rather than per input. *Per-edit hints that an edit preserves a value*: rejected for the reason above.

**For world up.** *Guess again on every derived clip*, what v0.9.0 did for slices, concatenations, resampled clips, `retarget` and most transforms: rejected because a slice, a resampled clip or a transformed clip could then report a different up than the clip it came from, and `harmonize` could flip an axis between its stages. *Turn the guess into an override on the derived clip*: rejected because the derived clip would then claim that the user chose the axis, and `world_up_inferred` and the docs could no longer say it was guessed; hence the third state.

## Consequences

Code that edited an owned node, assigned `bvh.nodes` or `bvh.root`, or relied on `children` or a channel order being a list must build a new skeleton and a new `Bvh`, through `bvh.copy(nodes=table)` when the motion stays. A reference to an old node object keeps the old values after an in-place transform, since the clip now holds new nodes; this is documented, not designed around. A derived clip whose own first frame would be guessed differently reports its source's world up; `world_up_inferred` still runs the inference fresh, to see what the guess would be. Pickles made before v0.10.0 are not supported, since they hold the old attribute layout, the forward-kinematics array included. Each is listed with its migration under the breaking changes of v0.10.0 in the CHANGELOG.
