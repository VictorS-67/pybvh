# Orientation has two frames, the skeleton's and the world's, and a report says what was measured

What a clip says about which way is up, left and forward comes from two sources: the rest pose, the skeleton with every rotation zero written in the file's coordinates, and the motion, which places that skeleton in the world frame by frame. Through v0.9.0 the code treated the rest pose as if it stood in the world: `rest_forward` removed world up from the rest pose's leftward and crossed it with world up, and the facing chain removed rest up at one stage and world up at the others. Most fallbacks in that chain were also silent. From v0.10.0 the orientation a clip implies is computed in one private module, `_orientation`, from plain data, with `Bvh` as its only adapter, under four decisions.

## Decision

**1. Two frames, and no computation combines an axis of one with an axis of the other.** The *skeleton's own frame* holds the facts read from the rest pose alone, never from world up: rest up (the main axis from the root to a joint whose name holds head, neck, chest or spine as a word, else the axis opposite the legs, the L/R pair nearest the root, else the axis of largest spread), rest left (the rest pose's L/R geometry measured against rest up) and rest forward = rest left × rest up. The *world frame* holds the facts read from the motion against world up: world up itself, the facing and the heading. The rest pose is never read as world coordinates. The one thing that carries a skeleton fact into the world is the root rotation of a frame: the heading is the root rotation applied to rest forward, projected on the ground. `mirror` and the rest reorientations work in the skeleton's frame: `mirror` reflects along rest left, and `reorient_rest_forward` rotates the rest pose about rest up and refuses a target parallel to it.

**2. One facing chain per frame, in the world frame.** For each frame it produces a leftward measured against world up: the frame's own leftward from its L/R pairs; where that is unreadable (the left/right axis is vertical), the root's heading at that frame, when rest forward is measured (the heading of a defaulted rest forward measures nothing); where that is unreadable too, the house default, stored once as a leftward. Forward is always left × up, so forward × left = up on every row, fallback rows included, and `left_at` and `forward_at` cannot disagree. The fallback rows keep `FacingFrame.valid = False`, and the warning on a degenerate frame names the frame. The heading is `NaN` on a frame where its projection on the ground is too short to read.

**3. A report says, for each orientation fact of the clip, whether it was set, measured or defaulted.** `bvh.orientation_report` returns a frozen `pybvh.OrientationReport`: `rest_up` with `rest_up_source` (`"named_joint"`, `"leg_pair"`, `"largest_spread"`, `None`), `rest_left`, `rest_forward` with `rest_forward_source` (`"lr_geometry"`, `"default"`), `world_up` with `world_up_source` (`"set"`, `"first_frame"`, `"rest_up"`, `"default"`) and `world_up_inherited`, and `lr_mapping_source` (`"set"`, `"names"`, `None`). The existing members read from it; `has_lr_geometry` is `rest_forward_source == "lr_geometry"`. Per-frame facts are not in it: `forward_at`, `left_at` and `facing_frame` carry them, with `valid` as the per-frame mark. The orientation warnings that exist stay and fire when the defaulted fact is read, never when the report is filled: world up defaulted and the rest pose and the first frame disagreeing on world up, once per guess, and the facing defaulted, which splits along the two frames into rest forward defaulted (read from `rest_forward`) and the facing defaulted on a skeleton with no L/R pairs or on frames whose leftward and heading are both unreadable (read from `forward_at`, `left_at`, `facing_frame`). Each points to the report, except the one about frames, which names them and points to `FacingFrame.valid`, since the report holds no per-frame fact.

**4. World up guessed from rest up stays, as a labelled guess.** When the first frame cannot decide world up, it is still guessed from rest up, the one place a skeleton fact reaches the world without a root rotation. It is a guess, not a combination of axes, and the report labels it `world_up_source == "rest_up"`.

## Why

**The rest pose's coordinates are not world coordinates.** The rest pose is written in the file's coordinates with every rotation zero; only the motion says how it stands in the world. A file can author its rest pose in another convention than its motion, and reading the rest pose against world up then names a direction the body never faces. On `bvh_test3` (world up `+z`) the rest pose alone gives rest up `+y` and rest left `+x`, so the skeleton faces `+x` × `+y` = `+z`; v0.9.0's `rest_forward`, forced perpendicular to world up, was `-y`, the direction of the rest pose's feet. The heading built on it lay almost along world up on every frame (median vertical component 0.985 over 100 frames) and its median gap to the body's measured facing (`facing_frame().forward`) was 9.7°; with the skeleton's own forward as the reference the gap is 2.3°. Over the maintainer's corpus of 23,020 clips, v0.9.0's `rest_forward` equals the skeleton's own forward on all 22,945 whose rest up is world up, differs on all 51 whose rest pose is rotated against the world, and is a warned default on 24 whose world up was guessed wrong from a first frame that is not upright, where the skeleton's own forward is measurable. Keeping the frames apart changes no value on the clean files and corrects the others.

**Two ups in one chain gave answers outside the frame.** The v0.9.0 chain behind `left_at` fell back to the rest pose's leftward measured against rest up, with no check against world up, so on a frame whose left/right axis is vertical `left_at` could return world up itself while `forward_at` fell to the house default. With one up per chain and forward derived from the leftward, every row is a right-handed basis with world up.

**`mirror` is a skeleton operation.** It reflects the offsets across the skeleton's own sagittal plane, and the motion follows by the same reflection, so the result is a valid mirror whatever world up says. On the 24 corpus clips above, the rest pose's left/right axis lies along the guessed world up, so a leftward measured against world up does not exist there, while rest left does; on the one whose true up could be measured from its motion, mirroring along rest left gives the same clip as mirroring the file loaded with that true up (largest difference 0.0). `mirror` would come out wrong only on a rest pose whose left/right axis is vertical in the real world, a body authored lying on its side, which the corpus does not hold.

**A fallback standing in for a measurement must be distinguishable** (`CODING_STANDARDS.md`). Through v0.9.0 three fallbacks were silent (world up from rest up, rest up from the largest spread, `left_at` from the rest pose) and the others were signalled three different ways (a warning, `has_lr_geometry`, `FacingFrame.valid`). One report covers every clip-level fact in one place, and the per-frame facts keep the one per-frame signal they already had.

**The rest-up guess for world up is the best evidence left.** When the first frame cannot decide, the alternative is the house default `+y`, which is no evidence at all, while rest up is world up on 22,945 of the 23,020 corpus clips. Improving the first-frame rule itself is a separate change (#115).

## How it sits with ADR 0003

ADR 0003 stands. The report is one more row of its derived-state table, and the setting of a user L/R mapping becomes one more input, with one more event, *the L/R mapping setting changed*:

| Derived value | Computed from | Cleared by |
| --- | --- | --- |
| orientation report | skeleton, L/R mapping setting, world-up override, guessed world up | skeleton changed, world-up override changed, user replaced the motion, L/R mapping setting changed |

Whether `world_up` has warned about a guess is held beside the guess and cleared with it, so each guess warns once. pybvh's own motion writes do not clear the report, since none of them changes the rest pose or which way is up (ADR 0003, decision 3). World up is still guessed once and inherited: a clip derived from another reports the same world up, `world_up_inherited` says so, and `world_up_source` keeps the source of the original guess, so copies and pickles carry the guess's source with the guess. Per-frame results (the facing basis, the heading) are not derived state: they scale with the frames, and the forward-kinematics positions they read already are.

## Considered options

**For `mirror`.** *`mirror` reads the rest pose's leftward measured against world up, and raises when there is none*, so that one leftward serves the whole package: rejected because it would raise on the 24 corpus clips above, which `mirror` mirrors correctly today, and gain nothing on the others, where the two leftwards agree. It was first decided on a misreading: the mirrored clip looked upside down when measured along the guessed world up, which for those clips is the wrong axis.

**For the facing chain.** *A middle stage that falls back to the rest pose's leftward*, measured against rest up (v0.9.0) or against world up: rejected. Against world up it reads the rest pose as world coordinates. Against rest up it is the two-ups defect above, and it never added an answer: over every corpus clip under all six world-up values (138,120 cases) it returned no forward where the rest pose's leftward measured against world up had none, because when that leftward is vertical in the world the rest-up stage snaps onto the same vertical axis, and its cross product with world up is zero. The root's heading at that frame is a measurement of the same frame instead, and is often readable when the left/right axis is vertical: on its side, a body's chest usually still faces a horizontal direction. *Left = up × forward*, deriving left from forward: rejected because up and the leftward are the two robust axes (up settled once, the leftward the only direction measured from the body) and forward is the derived one.

**For the report.** *One `*_source` member per fact on `Bvh`*: rejected for adding four or five members where one value says it all. *New warnings for the silent fallbacks*: rejected as noise on clips that load cleanly today; the report covers them. *A separate validity mask for the heading*: rejected because it changes `root_trajectory`'s return type, where `NaN` follows the `geometry` module's policy for data degeneracy.

## Consequences

`rest_forward` changes value on a rest pose rotated against the world (`bvh_test3`: `-y` becomes `+z`), and the heading follows the body there. `reorient_rest_forward` turns about rest up instead of world up. The heading is `NaN` where it cannot be read, and the `NaN` spreads into the neighbouring heading-velocity samples. Values are unchanged wherever rest up is world up, and `mirror`'s output is unchanged. Each change is listed with its migration in the v0.10.0 CHANGELOG.
