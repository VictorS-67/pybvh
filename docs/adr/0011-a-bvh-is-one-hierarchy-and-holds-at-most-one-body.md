# A `Bvh` is one hierarchy, and it holds at most one body

Through v0.9.0 pybvh read node 0 as the body. Up was the direction from the root to the head, the travel was the root's, and the size was the distance from the feet to the root. That is right when the root is the hips. It is wrong when an exporter puts a node above the body or beside it: a reference root that never moves, a 3ds Max `Bip01` root with a `Footsteps` helper beside the hips, a reference root that carries props, or Blender's `CHANNELS 0` root above several parentless bones. Under such a root a hierarchy can also hold two figures, and then every body-level number was a silent blend of the two. Nothing in the vocabulary named what those places of the code meant. Issue #205 names it, under the decisions below. ADR 0012 records how the body is found.

## Decision

**1. A `Bvh` is one hierarchy and its motion, whatever the hierarchy holds.** A hierarchy holds at most one body: the one articulated figure that the body-level operations describe. A skeleton can hold nodes outside the body: a root above it, a prop, a helper, a second figure. The body starts from the body anchor, a joint that a rule finds or that the user sets (ADR 0012). There is no new class.

**2. An operation is body-level or hierarchy-level.** An operation is body-level when it reads the body anchor, the head joint, the feet or the L/R geometry. Every other operation is hierarchy-level: it treats all nodes alike and needs no body.

- Body-level: the world-up guess, rest up, rest left, rest forward, the facing, the heading, `root_trajectory`, the `centered="skeleton"` and `centered="first"` modes, `auto_detect_feet`, `foot_contacts`, `ground_contacts`, `skeleton_size`, the gait descriptors and `mirror`.
- Hierarchy-level: reading, writing, forward kinematics, the derivatives, slicing, concatenation, `resample`, the Euler orders, `scale`, `extract_joints`, the bounding volumes, the scene ground and drawing.

**3. A clip with no body works at the hierarchy level and refuses the body level.** When the rule finds several candidates of comparable size, the clip has no body until the user names one. `bvh.body_anchor` is then `None`, and `orientation_report.body_anchor_source` is `"ambiguous"`. Neither raises. Each body-level operation raises `ValueError`, the type of pybvh's other refusals of an operation on a clip. Its text names the candidates and the way out, `bvh.body_anchor = ...` or `body_anchor=` at load. When the candidates share a name with another joint, a name selects none of them, so the text names the candidate through the report, `bvh.body_anchor = bvh.orientation_report.body_anchor_candidates[0]`. The hierarchy-level operations work as on any clip. The scene ground, drawing, `verticality` and `segment_axis_angle` read world up, and the world-up guess is body-level. So they raise until the user sets `world_up` or names the anchor. Once the user names the anchor, every operation describes that figure, and the user can name the other one afterwards. The static root does not change this: two figures under a root that moves are two candidates of equal size too.

**4. The reader still refuses a second `ROOT`, and says how many hierarchies the file holds.** A file with several `ROOT` blocks is valid BVH, but a `Bvh` is one hierarchy. The error gives the count of the file's `ROOT` blocks, counted up to the `MOTION` line: `Second ROOT 'Other' at line 16 in file walk.bvh: the file holds 2 hierarchies (ROOT blocks), and a Bvh holds one`. Through v0.9.0 it said "pybvh models single-root skeletons only", which reads as a limit of the skeleton, not of the file.

## Why

**The BVH format lets a file hold several hierarchies, and exporters write several figures under one root.** The two classic descriptions of the format say so. The University of Wisconsin course page on the format ("Biovision BVH", section "Parsing the file") says: "After this hierarchy is described it is permissable to define another hierarchy, this too would be denoted by the keyword "ROOT". In principle, a BVH file many contain any number of skeleton hierarchies." Meredith and Maddock, "Motion Capture File Formats Explained" (Department of Computer Science, University of Sheffield, Technical Report CS-01-11, 2001), section 3.1, page 6, say: "The ROOT keyword indicates the start of a new skeletal hierarchical structure and although the BVH file is capable of containing many skeletons, it is usual to have only a single skeleton defined per file." Blender's BVH exporter (`scripts/addons_core/io_anim_bvh/export_bvh.py`, `write_armature`) writes one hierarchy per file. When the armature has more than one bone without a parent, it writes "a dummy parent node, with a dummy key name" (its comment), `ROOT __0` with `OFFSET 0.0 0.0 0.0` and `CHANNELS 0`, and writes each parentless bone below it. So one hierarchy can hold a body and its IK targets, a body and a prop, or two figures.

**A body is a reading of the hierarchy, not a property of the file.** pybvh can find the body from the names and the shape of the hierarchy, but it can be wrong, and it cannot always choose. A model in which a clip is one body would make the reader cut or refuse a valid file on that inference. A model in which a clip is one hierarchy keeps the file as it is: the reader never cuts or refuses a hierarchy because of what the rule finds, and the inference is visible (`orientation_report`) and correctable (`bvh.body_anchor = ...`).

**A blend of two figures is a wrong answer that looks like a right one.** On `two_figures_moving_root` in the synthetic corpus, read with the root as the body, `auto_detect_feet` returned the toes of both figures, and the travel was the root's, which carries both. A refusal that names the candidates costs the user one line, and it never gives a number that describes no figure.

## Considered options

- **One `Bvh` per body, with the reader cutting or refusing a file on an inference from names and shape**: rejected. The reader would alter or refuse a valid file because of a guess. A write of the result would not give back the file that was read.
- **A container object beside a body object**: rejected. It adds a public class and splits one clip's motion, settings and derived state (ADR 0003) across two objects. Each hierarchy-level operation would need a home on one of them.
- **Reading several `ROOT` blocks under an invented root**: rejected. It adds a node that the file does not have, so a write of the clip would give a file with one hierarchy where the file read had several. Cutting one figure out as its own clip is #201, and reading several `ROOT` blocks as several clips is not planned.

## Consequences

A clip that holds two figures of comparable size raises on its first body-level call, where it gave a blend. One line names the figure. A file with several `ROOT` blocks is still refused, and its error says how many it holds. No function or class is added for the body. The CHANGELOG of v0.10.0 lists each change with its way out.
